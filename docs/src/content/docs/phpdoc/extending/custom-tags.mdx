None of the tags listed in the sidebar are special-cased inside the parser.
`@param`, `@see`, `@template` and every other tag are declared the exact same
way, and a tag of your own is added through that very same mechanism: a 
**[platform](/phpdoc/platforms/)**.

Adding one takes a few small parts that fit together — a tag object, its
definition, the grammar the definition is written in, the combinators it leans
on, and the platform that registers the lot. This page shows how they connect;
each part is covered in depth on its own page, linked as it comes up and again
under [Where to Go Next](#where-to-go-next).

## Adding a tag in practice

Recognizing a `@money` tag of your own — documenting a monetary amount and a
currency — starts from the shape of the line it should accept:

```
"@money" <Amount> <Currency> [ <Description> ]
```

Describing that shape is all the parser needs: it becomes the tag's
**specification**, written with the [`Spec`](/phpdoc/extending/grammar/) grammar DSL — an
integer, then a name, then an optional description:

```php
use TypeLang\PhpDoc\DocBlock\Combinator\DescriptionCombinator;
use TypeLang\PhpDoc\DocBlock\Combinator\IntegerCombinator;
use TypeLang\PhpDoc\DocBlock\Combinator\NameCombinator;
use TypeLang\PhpDoc\DocBlock\TagDefinition\Spec;

$spec = Spec::sequence(
    Spec::rule(IntegerCombinator::NAME, 'amount', 'Amount'),
    Spec::rule(NameCombinator::NAME, 'currency', 'Currency'),
    Spec::maybe(
        Spec::rule(DescriptionCombinator::NAME, 'description'),
    ),
);
```

Each `Spec::rule()` takes the combinator that reads that part of the line, the
alias its captured value is stored under, and — optionally — the name (e.g. 
`Amount` or `Currency`) it renders as in the grammar above.

<Aside type="tip">
The building blocks named here — `Integer`, `Name`,
`Description` — are combinators. See [Grammar](/phpdoc/extending/grammar/)
for the `Spec` DSL and [Combinators](/phpdoc/extending/combinators/) for
the blocks it reads with.
</Aside>

The value object the parsed line becomes is a small, immutable [tag](/phpdoc/extending/tags/)
class:

```php
use TypeLang\PhpDoc\DocBlock\Description\DescriptionInterface;
use TypeLang\PhpDoc\DocBlock\Tag\Tag;

final class MoneyTag extends Tag
{
    public function __construct(
        string $name,
        public readonly int $amount,
        public readonly string $currency,
        ?DescriptionInterface $description = null,
    ) {
        parent::__construct($name, $description);
    }
}
```

A specification is not used on its own — it is declared inside a
[definition](/phpdoc/extending/definitions/), which pairs it with a `create()` method turning a
match into that tag object:

```php
use TypeLang\PhpDoc\DocBlock\TagDefinition\TagDefinition;
use TypeLang\PhpDoc\DocBlock\TagDefinition\TagPayload;

final class MoneyTagDefinition extends TagDefinition
{
    public static function getCanonicalName(): string
    {
        return 'money';
    }

    public function __construct()
    {
        parent::__construct(self::getCanonicalName(), Spec::sequence(
            Spec::rule(IntegerCombinator::NAME, 'amount', 'Amount'),
            Spec::rule(NameCombinator::NAME, 'currency', 'Currency'),
            Spec::maybe(
                Spec::rule(DescriptionCombinator::NAME, 'description'),
            ),
        ));
    }

    public function create(string $name, TagPayload $result): MoneyTag
    {
        return new MoneyTag(
            name: $name,
            amount: $result->get('amount'),
            currency: $result->get('currency'),
            description: $result->find('description'),
        );
    }
}
```

The aliases declared in the spec — `'amount'`, `'currency'`, `'description'` —
are exactly how `create()` reads the matched pieces back: the `TagPayload` it
receives is keyed by them, so `$result->get('amount')` returns whatever the
`amount` rule captured.

<Aside type="tip">
`get()` fetches a required capture, `find()` an optional
one, and `getAll()` every value of a repeating one. See
[Captures](/phpdoc/extending/grammar/#captures).
</Aside>

Finally, the definition is registered by contributing a [platform](/phpdoc/platforms/)
to the parser:

```php
use TypeLang\PhpDoc\DocBlockParser;
use TypeLang\PhpDoc\Platform\Platform;

final class MoneyPlatform extends Platform
{
    public function getTags(): iterable
    {
        return [
            MoneyTagDefinition::getCanonicalName() => new MoneyTagDefinition(),
        ];
    }
}

$parser = new DocBlockParser(platforms: [
    new MoneyPlatform(),
]);

$block = $parser->parse('/** @money 100 USD */');

$block[0]; // MoneyTag { amount: 100, currency: "USD" }
```

A platform's three methods register the three kinds of thing the parser needs:

* **`getTags()`** registers the [definitions](/phpdoc/extending/definitions/), keyed by each
  tag's canonical name.
* **`getCombinators()`** registers any [combinators](/phpdoc/extending/combinators/) the
  definitions reference that are not built in already (`@money` needs none).
* **`getAliases()`** maps an alternative spelling to a canonical tag name.

`Platform` is an abstract base whose three methods return empty lists, so a
platform overrides only the ones it needs; implementing `PlatformInterface`
directly works just as well.

<Aside>
The constructor loads only the platforms passed to it: no built-in platform,
not even the `StandardPlatform`, is added on its own. To get the
full built-in set together with your own platform, pass it to
[`DocBlockParser::createDefault()`](/phpdoc/platforms/) via its
`$additionalPlatforms` argument:

```php
$parser = DocBlockParser::createDefault(additionalPlatforms: [
    new MoneyPlatform(),
]);
```

</Aside>
